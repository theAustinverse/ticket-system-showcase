# 年度盛會售票系統｜作品說明

一套為實體年度活動打造的線上售票系統：搶票當下數千人同時湧入，固定數量的座位一張都不能多賣；活動當天憑每個座位的 QR 入場。

- 正式站：<https://www.ts-annual-event.com>
- 原始碼：不公開（本儲存庫只放說明文件與流程圖）
- 開發期間：2026-07-11 起，持續更新至 2026-11

## 我怎麼思考這套系統

我沒有程式設計背景，這套系統是我和 Claude Code 以 vibe coding 的方式一起做出來的。我負責決定產品要怎麼運作、哪些地方不能出錯，並逐頁驗收；程式由 Claude 撰寫。

### 產品思維：讓大家公平地搶票

> 我最在意的是讓大家公平地搶票。

這個目標落實成下面這些規則：

- **排隊前必須先登入**：排隊憑證綁定本人帳號，轉給別人也不能用來插隊。
- **一個 Gmail 信箱只能有一個帳號**：擋掉用分身帳號多搶。
- **每個帳號只能有一席本人票**：一個人不能用自己的名字佔好幾個座位。
- **轉讓要雙方都接受才算成功**：票只會在雙方同意時轉手。

### 系統思維：先守住絕對不能出錯的地方

> 絕對不能出錯的是：不能超賣，和個資不能外洩。

**不能超賣**
- 庫存用單一原子操作扣減，同時湧入再多人也不會多賣。
- 排隊室只控制速度，防超賣交給庫存扣減，所以放行速度可以放心調整。
- 開賣中不能重算庫存，避免把已經賣出的座位放回去重賣。

**個資不能外洩**（系統裡有很多夥伴的 Email 與真實姓名）
- 轉讓時，收票人只看得到邀請需要的資訊。
- 購票者看不到管理員的備註。
- 客服小幫手拿不到任何使用者和訂單資料。
- 忘記密碼時，系統不會透露某個信箱有沒有註冊過。
- 作品公開前，聯絡資訊改成馬賽克，收款資訊改成星號。

### 改良方式：看試用回饋，自己逐頁測試

> 我靠試用回饋和自己逐頁測試，決定下一步要改什麼。

- **試用回饋**：網站上線後，先請朋友和團隊夥伴試用，再依回饋新增功能、優化流程、介面與轉場。
- **逐頁測試**：我在畫面上發現問題就回報修正。例如點頁尾連結後新頁面停在中段，改成換頁回到頁首；首頁看不到新的贊助選項，補上首屏提示。
- **壓力測試**：我要求在正式環境做壓測。2,500 名模擬使用者同時進入，150 秒內只放行約 160 人，依這個結果調高放行速度。
- **公開公告**：每次功能新增或調整，都公告在網頁上讓大家知道。

每一項決策的來龍去脈和依據，見[更新日誌與完整紀錄](docs/04-changelog.md#產品決策紀錄)。

## 這個系統做了什麼

- **搶票不超賣**：庫存放在 Redis，用單一原子操作扣減；資料庫只記錄已經成功的訂單。
- **虛擬排隊室**：控制同時湧入下單的人數，只負責速度與體驗，不負責防超賣。
- **每席一張入場 QR**：轉讓後舊 QR 立即失效；同一張 QR 只能報到一次。
- **兩步驟轉讓**：收票人接受前，票券不會移動。
- **後台**：波次與票種設定、訂單修正、報到名單、贊助對帳、客服回覆。
- **客服小幫手**：只根據 FAQ 回答，答不出來就轉給真人。
