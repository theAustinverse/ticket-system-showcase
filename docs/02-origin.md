# 2. 專案的起源及如何構思

## 背景

我所在的團隊每年都會舉辦年度盛會。年初我報名擔任盛會行政組的組員，負責行政與票券事務，協助大家搶購票券。

## 原本的做法

往年搶票都是用 Google 表單：把表單丟到群組讓大家填資料，再取最前面搶到的 100 名、200 名或 300 名作為參加活動的夥伴。

這個流程非常複雜，表單還要另外整理，大概會花掉行政組兩到三週的作業時間。

## 提案

行政組開會時，我提議用 Claude Code 以 vibe coding 的方式做出一個售票網站：有完整的搶票介面，讓大家體驗搶票的快感，並設計好 UI/UX，讓大家容易操作。

## 想要解決的問題

1. **避免超賣**：像一般演唱會售票系統一樣鎖定票數，讓大家在上面購買。
2. **票券轉讓**：有些夥伴到接近活動日期才發現無法參加，可以直接在系統上轉讓。

## 為什麼不用現成的售票平台

1. 這是內部活動，不想完全對外公開。
2. 上架到外部售票平台還要另外花錢。

## 怎麼開始的

我沒有任何相關經驗，也沒有程式設計背景。一開始只是在 Claude Code 裡詢問該怎麼做，再一步一步說出我的想法和目標。

網站上線後，我先請朋友和團隊夥伴試用，看看還有哪些功能可以新增，以及流程、介面設計和轉場有哪些地方可以優化。

## 我和 Claude 的分工

我負責告訴 Claude 我想要的運作模式、產品架構和設計框架，再逐頁檢查介面，檢查整個流程設計、網站框架和安全性。系統裡有很多夥伴的 Email 帳號與真實姓名，所以安全性是我特別注意的部分。

每一項決策是誰提出的，詳見[更新日誌與完整紀錄](04-changelog.md#產品決策紀錄)。

## 我主動要求的功能

開發過程中，下面這些功能是我直接提出、要求加上的：

1. **環境壓力測試**：在正式環境模擬大量使用者同時搶票，依結果調整排隊室的放行速度。
2. **排隊前必須先登入**。
3. **波次結束後，剩下的票自動轉到下一波**。
4. **轉讓票券要雙方都接受才算成功**。
5. **所有功能的新增與調整都公開公告**：放在網頁上讓大家看。

各項的上線日期與實作方式，見[更新日誌與完整紀錄](04-changelog.md#產品決策紀錄)（D16、D29～D32）。
